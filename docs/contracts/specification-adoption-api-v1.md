# Specification adoption API v1 — review candidate

Owner: Cai Runchen / M2. Work item: SCRUM-55 under SCRUM-48.

`POST /api/catalog/products/{id}/formula-adoptions` explicitly creates and releases
a new formula snapshot using a newer released specification. It requires both
`DATA.MAINTAIN` and `FORMULA.RELEASE` through the existing CatalogIntegration.
Identity comes from the configured identity adapter; the body contains no actor.

```json
{
  "sourceFormulaVersionId": "formula_1106285_v1",
  "targetSpecificationVersionId": "spec_chocolate_v2"
}
```

Both fields are required nonblank IDs. The product path must exist, and the source
must belong to that product, be RELEASED, and still be its current formula. The
target must be RELEASED and effective in UTC, belong to a material used by the
source, and have a greater specification version number than every replaced item.
The source's other pinned specifications must also remain released and effective.
A replaced historical specification may be RETIRED: the new snapshot pins the
eligible target while the source snapshot retains that historical reference.

HTTP 201 returns the committed formula detail in the existing Catalog snake_case
format, including `formula_version_id`, `product_id`, `version_number`,
`lifecycle_status: RELEASED`, `is_current_released: Y`, release metadata, target
`data_provenance_id`, and `items`. IDs are generated by the server. Version numbers
follow the existing product allocation rule: highest allocated version plus one;
an existing draft retains its own number and content.

In one transaction, the operation locks the product, validates the exact source
and specification references, creates a fresh formula and item IDs, releases that
formula, updates `product.current_formula_version_id`, and records
`FORMULA_CREATED`, `FORMULA_RELEASED`, and `FORMULA_SPECIFICATION_ADOPTED` events.
The request adapter records source, target specification, and new formula IDs in
the adoption audit payload, using the target specification's existing provenance.
An exception, including audit failure, rolls back all writes.

Every source item is copied with its original material, sequence number, quantity,
and unit. All items for the target material pin the new specification; other
specification references stay unchanged. Earlier formula content, item rows,
release actors, and release timestamps stay unchanged. Only the old formula's
current-selection flag changes to `N`, as in the existing release operation.
Labels, declarations, review tasks, and publication records are unaffected.

Application errors retain exactly `code`, `message`, `traceId`, and `evidenceId`.

| HTTP | Code | Meaning |
| --- | --- | --- |
| 400 | INVALID_REQUEST | Missing/malformed body, invalid IDs, or empty source items. |
| 401 | AUTHENTICATION_REQUIRED | Existing identity adapter cannot authenticate the caller. |
| 403 | AUTHORIZATION_DENIED | Caller lacks either required permission. |
| 404 | RESOURCE_NOT_FOUND | Product path does not exist. |
| 409 | CURRENT_FORMULA_CHANGED | Source is no longer the product's current formula; refresh before retry. |
| 409 | SPECIFICATION_ALREADY_ADOPTED | Source already contains the requested target specification. |
| 409 | DATA_CONFLICT | Existing Catalog database conflict mapping. |
| 422 | INVALID_REFERENCE | Body references an unavailable formula or specification. |
| 422 | SOURCE_FORMULA_PRODUCT_MISMATCH | Source belongs to another product. |
| 422 | SOURCE_FORMULA_NOT_RELEASED | Source is not released. |
| 422 | SPECIFICATION_MATERIAL_MISMATCH | Target material is absent, or a source item's pinned specification belongs to another material. |
| 422 | SPECIFICATION_NOT_RELEASED | A referenced specification is not released. |
| 422 | SPECIFICATION_NOT_EFFECTIVE | A referenced specification is not effective yet. |
| 422 | SPECIFICATION_VERSION_NOT_NEWER | Target would repeat or downgrade a source item's specification version. |
| 503 | CATALOG_INTEGRATION_UNAVAILABLE | Existing Catalog identity/audit adapter is not configured. |
| 500 | INTERNAL_ERROR | Unexpected failure, including audit failure; transaction rolls back and internal details stay in server logs. |

This additive Catalog endpoint does not change the frozen impact API's error
matrix. Cross-module review remains required before treating this candidate as
accepted.

## M1 consumption after adoption

SCRUM-77's relevance port selects `FormulaItem.supplier_material_id` from the
product's current released formula. Adoption keeps those material IDs, so it does
not alter the relevant-product set. The returned current formula is the adopted
N+1. In an impact finding, however, `currentFormulaVersionId` means the formula N
pinned by the current published label; `proposedFormulaVersionId` is the adopted
N+1. Read these through the existing label and formula ports using their exact IDs.

After adoption, a published-label snapshot can have `isCurrent() == false` because
its formula is no longer current. That flag is a validation-eligibility guard; it
does not mean the published label is absent. SCRUM-78 must retain its declarations
for the before/after comparison. Classification and publication remain with M1/M4.

At baseline `e53f7b0`, `RelevantProductLookupPort` has no production adapter. PR #56
provides the SOY golden oracle and lookup semantics, not that adapter. This runtime
dependency requires its owner to supply the adapter before discovery runs end to
end; SCRUM-55 does not implement the discovery or classification service.
